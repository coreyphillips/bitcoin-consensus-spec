# Results

What has been tested, how, and what was found. Everything here is against Bitcoin Core v32.1 (commit `f0de87f040621468b956f01f526a43a010310501`). Numbers are copied from the tools' output.

The `peer-sync` suite (`conformance/PROTOCOL.md` section 5.1) needs a node that keeps synchronizing after its peer sends it an invalid block. The reference's synchronization loop (chapter 14 section 14.5) stops there by design, so the suite was checked with Bitcoin Core v32.1 itself as the node (`conformance/recorder/core_sync_node.py`, `-connect` to the runner, BIP324 version 2). Of the 2,922 corpus blocks whose parent is on a scenario's final chain, Core rejects 2,882 in proposal mode (the other 40 are valid side branches). Core passed all 3,111 checks: 2,902 in the follow mode (every rejected block, and each scenario's final tip) and 209 in the ibd mode (a fresh node per rejected block, at most 32 per scenario), in about 25 minutes on an Apple M5 Pro.

The derived expectations come from Bitcoin Core's own interpreter compiled from the pinned source (`conformance/oracle-core`), which passes the same script and transaction suites. The interop suite's check for misbehaviour was itself tested: a fake node that sends a `getdata` with 50,001 entries is reported ("Misbehaving: peer=0: getdata message size = 50001"). The interop suite leaves out, by a stated rule, a scenario whose final chain has blocks dated more than two hours after the current time, because a live node judges time by its real clock. No scenario meets the rule now. `mining_basic.node0`, whose blocks are dated up to 21 hours after its recording, met it until 2026-11-09 18:44 UTC. A scenario recorded anew with mock time ahead of the clock will meet it again until its blocks are no longer that far ahead. The vector suites passed on the reference's first complete run; so did the first 16 corpus scenarios. Every corpus scenario is replayed with restarts re-delivered (33 restarts, 10,781 re-delivered events), as `conformance/CORPUS.md` section 4 prescribes.

## 2. Independent reviews

Three reviewers, each a fresh agent given the repository and the Bitcoin Core v32.1 source, audited one part of the specification against Core and tried to make the reference disagree with Core.

The tools these reviews wrote were not kept, so the figures below are a record of one-off runs and cannot be reproduced exactly. `conformance/tools/differential.py` repeats their method for scripts, transactions, proof of work and signet: seeded random requests sent to both the reference and the oracle built from Core's source. The weekly `core` workflow runs it with 20,000 requests per area. `conformance/tools/multibranch.py` repeats the 500 random multi-branch scenarios: seeded random regtest block trees sent to both the reference and a v32.1 bitcoind through `core_chain_harness.py`, with the tip, the chain tip set and the UTXO set hash compared after every step. The weekly `core` workflow runs 100 of them. On 2026-11-19, 500 scenarios with seed 1 (104,443 steps, 1,663 reorganizations) were identical, and so were 200 with seed 20261119. For chapters 09 and 13 the repeatable evidence is now the `pow` and `signet` suites (section 3).

**Chapters 02 to 07 (scripts and signatures).** Differential fuzzing of the reference against Core's interpreter (about 2.5 million generated cases through the harnesses, and about 194 million in-process checks) found no case where the two disagree. The review found four prose errors, all fixed: the order in which `OP_CHECKMULTISIG` matches signatures to keys was described backwards (the code was right), chapter 04 named the wrong error for number decoding (`UNKNOWN_ERROR` instead of `SCRIPTNUM`), a cross-reference, and the unstated precondition that `WITNESS` implies `P2SH`. It also asked for a stricter harness (input sizes, ranges, lowercase hexadecimal), now implemented.

**Chapters 08 to 13 and 15 (transactions, proof of work, blocks, chain state).** No consensus split and no chain selection difference: 500 random multi-branch scenarios against a v32.1 node (headers first, out of order delivery, spends across forks, invalidations, future timestamps, mutated copies) gave identical tips, chain tip sets and UTXO hashes; 61,200 random difficulty adjustment chains over all networks and 225,377 compact target and proof cases were identical to Core's own `pow.cpp`; 19 signet blocks with real signatures matched. Findings, all fixed: `process_block` reported `accepted` for a block its own activation found invalid (a reported reason only; the chain state was right), Core's script error is not deterministic when several inputs fail (now documented), unrequested blocks below the minimum chain work, the best header tie after an invalidation, sequence numbers after a restart, and the exception count in chapter 12.

**Chapter 14 (peer to peer), consistency and implementability.** Live runs of the reference node against bitcoind v32.1 matched tip and `hash_serialized_3` in every scenario tried (fresh syncs of up to 4,305 blocks with varied transactions, reorganizations while connected, with and without whitelisting), and bitcoind logged no misbehaviour. Findings, all fixed: the conformance runner passed an implementation that implemented nothing (unsupported checks now fail); `PROTOCOL.md` let implementations ignore `requested`, which changes the tip; chapter 14 said Bitcoin Core answers block requests with `notfound` (it never does, so a node built from that text could wait forever); `getheaders` answers, handshake rules, frame size checks and the end of a synchronization did not match Core; and several release attributions in Appendix C were wrong.

## 3. Mutation audit

Each mutant changes one rule in a copy of the reference (for example "treat the transaction version as signed in BIP68", "check the block weight before the witness commitment"). A mutant is caught when some suite fails. 105 of the 145 mutants break a quirk from Appendix A and name its item. The other 40 break a rule Appendix A does not list, such as the coinbase script length or a mainnet activation height. `run.py --items` prints the Appendix A items that no mutant breaks: 19 of 79. The mutants and the script that runs them are in `conformance/mutation`.

| Mutants | Caught by the vectors and corpus | Notes |
|---|---|---|
| 114 script, transaction, proof-of-work, signet and network parameter rules | 110 by a wrong verdict, 3 more by a wrong error identifier only | The other one cannot be caught: a taproot tweak at or above the curve order needs a tagged hash that large, which is infeasible to find |
| 44 block and chain rules | 34 by a normative tip check, 5 more only by the chain tip sets (a level the suite requires only with `--fail-on-tips`), 1 more only by the UTXO set hashes | The 5 change only the status of blocks off the active chain (descendants of an invalid block; unrequested low-work blocks kept in full; mutated blocks, low-work blocks and low-work headers from peers no longer dropped) and no active tip in any recorded scenario. The other 4 survive; they are probes of chapters 09 to 15 described below |

Every surviving mutant that could be caught, except those 4, led to new tests: 21 custom vectors (script and transaction edge cases, expectations from Core's own code) and a recorded scenario, `feature_spec_pitfalls` (three nodes with different activation options), of hand-built blocks delivered to Bitcoin Core v32.1: BIP68 with high-bit versions, legacy sigop counting at exactly 80,000, the subsidy halving boundary, negative block versions, the version floor where BIP34 is active and BIP66 and BIP65 are not, the 64-byte transaction ambiguity, the P2SH stack limit, the BIP94 timewarp boundary with full blocks, and the anti-denial-of-service work checks for blocks and headers from peers.

Skipping `FindAndDelete` of an empty signature in `OP_CHECKMULTISIG` was first recorded as impossible to catch, because an empty signature always fails. It is not. Deleting the `OP_0` from the script code decides whether another signature of the same operation verifies. That decides whether a badly encoded signature after it is reached (`SIG_DER`) or the operation returns false, which `OP_NOT` turns into success. Two custom vectors in `script-versions.jsonl` now catch it by a wrong verdict, one in each direction.

A review of three other published consensus implementations (btc-lean, Hornet and Bitcoin Commons, 2026-11-09) found no consensus rule missing from the specification, and one inaccurate sentence (the genesis outpoint, chapter 12 section 12.3). It also found bugs of eight kinds in those projects, each now a mutant (nine in all; Appendix A gains items 73 to 79, and the tapscript case is item 17): ECDSA R or S reduced modulo the group order, a well-formed oversized R or S treated as a script error, `OP_CHECKMULTISIG` checking encodings it never reaches, P2SH redeem scripts over 520 bytes, the push limit skipped in unexecuted tapscript branches, sigop counting stopped by a long push, the coinbase left out of the sigop cost, and a cap on transaction outputs. Three were already caught by the suites. The other six survived, or were caught only by an error identifier (a 32-byte R or S at or above the order treated as an encoding error), and are now caught by twelve new custom vectors and by part j of `feature_spec_pitfalls` (a transaction with 100,001 outputs), re-recorded from Bitcoin Core v32.1, replayed through it, and synchronized from bitcoind v32.1 by the reference node with identical results.

rbitcoin PR 1537 (2026-11-11) fixed a consensus split: during initial sync, after a write of several blocks was rejected and retried one block at a time, rbitcoin accepted a block that re-spent an output created and spent inside an earlier block. The corpus had no block of that shape, and a mutant of the same kind (`same-block-spend-not-persisted`: such an output stays in the UTXO set) was noticed only by the UTXO set hashes, which an implementation without a UTXO set does not report. Part k of `feature_spec_pitfalls` now re-spends such an output in the next block (both blocks requested and delivered together), through `submitblock`, three blocks higher, and next to a valid spend that must not survive the rejected block; the mutant is caught by normative tip checks. Part k was re-recorded from Bitcoin Core v32.1, replayed through it, and synchronized from bitcoind v32.1 by the reference node with identical results. Part k alone does not reproduce rbitcoin's bug: rbitcoin's corpus harness submits blocks one at a time. The `peer-sync` suite does. It serves the corpus to a node through the node's own synchronization, rejected blocks included; in its ibd mode a fresh node meets each rejected block at the end of its initial block download, delivered right behind its parent at the end of a burst as long as the node's download window. On `feature_spec_pitfalls.node0`, rbitcoin built from the parent of the fix's merge (`41be5e45f`) failed 7 of 8 runs: each failing run ended an initial sync with one to three of part k's four re-spend blocks as its tip, which Core rejects as `bad-txns-inputs-missingorspent`. Built from the merge (`87cf8a4bb`), it passed all 6 runs, and over the whole corpus it passed 3,106 of the 3,111 checks in 52 minutes; the other 5 are `feature_spec_pitfalls.node2`, which needs `-test=bip94`, a regtest switch rbitcoin does not have. A single run can miss the bug because rbitcoin only merges the two blocks into one write when its write stage is still busy when they arrive (section 5). After the follow mode's catch-up, rbitcoin drops a peer that sends it more than 16 MB in a second, even of blocks it asked for, and connects again; the suite's settle rule waits for that, so `feature_block_reorg`'s 1 MB blocks over loopback cost time but not a verdict.

An audit of chapters 05 to 07 (2026-11-17) applied the same method by script version: 90 one-line mutants, most of which switch a rule off for one script version only. 22 passed every default suite, also with `--fail-on-level2`, because almost no vector exercised an interpreter rule inside a witness version 0 script or a tapscript. They switched off the opcode, push and number size limits, strict DER, `OP_CHECKLOCKTIMEVERIFY` or `OP_CHECKSEQUENCEVERIFY` for one script version, broke the P2SH-wrapped forms of the witness program rules, or made legacy `FindAndDelete` remove a signature at any byte offset or only one of several consecutive copies. One of them, an unknown tapleaf version that skips the commitment check, makes every taproot output spendable by anyone. Nine more were missed by the script suites at the verdict level: one was caught there only by an error identifier, and the other eight only by the block corpus, which an implementation that has reached only the script suites does not run. 178 custom vectors (`conformance/vectors/custom/script-versions.jsonl`, expectations from Core's own code) now catch all 31 by a wrong verdict, and two more mutants by a script error only. The 33 are in `mutants.json`.

An audit of chapters 02 to 04 (2026-11-17) found nine more one-line mutants that passed every default suite, also with `--fail-on-level2`. They compared ECDSA's R.x with r without reducing it modulo n, accepted a hybrid key whose prefix does not match the parity of y, reduced a taproot internal key modulo p, took a 3-byte or 43-byte script for a witness program, kept the low 32 bytes of an oversized R or S, rejected long-form DER lengths without `DERSIG`, or accepted non-canonical CompactSize in the `fe` and `ff` forms. A tenth removed the 34 `OP_SUCCESS` opcodes that no script suite case decided; only the block corpus caught it. 211 custom vectors now catch all ten by a wrong verdict: 34 in `edge-cases.jsonl`, and every opcode from 0x4f to 0xff as a tapscript of its own in `script-versions.jsonl`. They are 12 mutants in `mutants.json`, since the R and S cases and the `fe` and `ff` cases are separate.

The same audit made 19 one-line probes for rules no mutant reached: 15 in chapters 09, 12, 13 and 15, the BIP30 and script flag exceptions of chapter 10, and the most-work rule of chapter 11. They are in `mutants.json` with the verdicts they get. 18 survive every suite at every level. The 19th, the coinbase flag left out of chapter 15's UTXO set hash, is caught only by the corpus UTXO set hashes. Every corpus scenario is regtest, which never retargets, gives every block the same work, and has none of the other networks' heights or exception blocks. So no repeatable suite tested difficulty adjustment, the signet block solution, most work against longest chain, the BIP30 and script flag exceptions, or the per-network parameters. The unit tests of chapter 09 caught two of the 18 (the compact encoding's sign step and `block_proof`), but a candidate implementation does not run them. The `pow` suite (`conformance/vectors/pow`, expectations from Core's own `pow.cpp`) now catches eight of them by a wrong answer: those two, the upper retarget clamp, the 2,015 intervals of a period, BIP94's base target, the 20-minute rule's boundary, the walk back over minimum-difficulty blocks and the proof-of-work limit. The `signet` suite (`conformance/vectors/signet`, expectations from Core's own `signet.cpp`) catches a ninth, the signet solution accepted whatever it is, and 12 more chapter 13 mutants added with it. A scenario in the corpus format (`conformance/vectors/chainwork`) catches a tenth, the longest chain taken for the one with most work: on a custom signet, a branch that retargets to four times the work overtakes a longer one, and Bitcoin Core v32.1 gives the same tips and chain work. It also catches a new mutant that adds regtest's work for every block whatever its `bits`. A mutant that leaves the signet check out of `check_block` passed every default suite, because the `signet` suite calls chapter 13's check directly. A second signet scenario in the corpus format (`conformance/vectors/signet/signet-blocks.jsonl.gz`) now catches it: blocks without a valid solution must leave the tip where it was, and Bitcoin Core v32.1 rejects them with `bad-signet-blksig` and gives the same tips. The `params` suite (`conformance/vectors/params`, expectations read from Core's own `CChainParams`) catches three more: mainnet's BIP66 and CSV heights off by one, and a halving interval of 210,001. A fourth, testnet4 without BIP94, was already caught by the `pow` suite's testnet4 retargets. It was recorded as surviving because it ran as a block mutant, which does not run `pow`. The `block-connect` suite (`conformance/vectors/block-connect`) catches three of the 4 survivors: the script flag exceptions ignored, the BIP30 exempt height moved and the BIP34-implies-BIP30 limit removed. The last survivor's note names the open issue for its missing test.

## 4. The blind implementation

`bitcoin-spec-node` is a Rust node written by an AI agent that was given only the specification package: `spec/` and `conformance/` (protocol, runner, vectors), without `reference/`. It was not allowed to read Bitcoin Core's source, BIPs, other implementations or Bitcoin libraries, and could use only generic crates and libsecp256k1 bindings. It is the same model family as the agent that wrote the specification, so it brings general knowledge of Bitcoin; the experiment tests whether the specification is enough to turn that into an exactly compatible node, not whether a reader with no background could do it.

First runs, before any fix:

| Milestone | Suites | First run |
|---|---|---|
| M1: consensus library and harness | all vector suites, 337,963 checks; 21 custom cases | all pass, identical error identifiers |
| M2: chain state | 16 corpus scenarios: 4,951 normative tips, 935 chain tip sets, 2,078 UTXO set hashes | all pass |
| After the specification errata from the reviews (old build, no code changed yet) | the re-recorded corpus, 18 scenarios: 5,114 normative tips | all pass |
| M3: the node (RocksDB, block and undo files, P2P) | `interop` against bitcoind v32.1 without a whitelist, 18 chains | 18 of 18 identical (tip, height, `hash_serialized_3`) |
| Corpus with the version floor and timewarp nodes | 20 scenarios: 5,275 normative tips, 1,230 chain tip sets, 2,288 UTXO set hashes | all pass |

Its own regtest scenarios against bitcoind (about 90,000 signed transactions of every standard output type, reorganizations while connected, and ten kills with SIGKILL during synchronization followed by restarts) also matched Bitcoin Core's tip and UTXO set hash.

It recorded five places where the specification was unclear (`SPEC_FEEDBACK.md` in its repository); all are resolved in the specification or the protocol. The errata it received during the experiment are the review fixes described in section 2; its log states which of them needed code changes.

Holdouts, run by the experiment owner on a fixed commit of the node, not by the agent (testnet4: `7ddd347`; mainnet: `1124fb7`):

| Network | Source | Comparison | Result |
|---|---|---|---|
| testnet4 | public peers from the DNS seeds | `hash_serialized_3` at heights 90,000, 120,000 and 150,000 against Bitcoin Core's values (chapter 15) | **identical at all three heights.** Every block from genesis to 150,000 fully validated, every script checked, in 68 minutes (2026-11-08) |
| mainnet | a local Bitcoin Core v32.1 node as its only peer | `hash_serialized_3` at heights 840,000, 880,000, 910,000, 935,000 and 965,000 against Bitcoin Core's values (chapter 15), then against that node's `gettxoutsetinfo` at a common tip | **identical at all five heights and at the tip.** Every block from genesis to 975,132 fully validated, every script checked (the node has no assume-valid), in 2 hours 26 minutes (2026-11-08) |

At the common tip, block 975,132 (`00000000000000000000d50927e773416b727bdb5706f62a8ec4a7006011a1a1`), both nodes reported `hash_serialized_3` `0139bed824c0ad6b70c60c63fa2bf09fdd06e02a957b4362d6a9889befe1c0ef` over 163,585,794 unspent outputs. The blind node computed its value after a clean shutdown and a restart from its database. The machine was an Apple M5 Pro (6 performance and 12 efficiency cores, 64 GB); the node verifies signatures with libsecp256k1 on every core, as chapter 02 section 2.11 allows.

## 5. Not covered

- The reference itself has validated mainnet and testnet4 *headers* from real peers, not their blocks: it keeps its state in memory and is written for clarity, not speed. Full block validation of both networks was done by the blind implementation (section 4).
- A full synchronization shows that the node accepts every block of the real chain and reaches the same UTXO set as Bitcoin Core at the compared heights. It does not exercise invalid blocks. The vector suites and the block corpus test their rejection through an implementation's harness, which may bypass the code its node runs during initial sync (one block per `submitblock` call, for example). The `peer-sync` suite delivers them through the node's own synchronization, but only blocks recorded in the corpus whose parent is on the scenario's final chain, and in its ibd mode, by default, 32 per scenario. Whether a node that validates in batches puts a rejected block in the same batch as the blocks before it depends on the node's timing: the suite makes that likely (section 3), not certain.
- The `pow` suite tests difficulty adjustment as a function of a parent and its ancestors. No offline suite delivers a header chain across a retarget, or a minimum-difficulty block, through `chain_process_headers`; only `headers-live` does, and it is run by hand.
- The `block-connect` suite connects a few small mainnet and testnet3 blocks, not mainnet block 692261 (the taproot flag exception), the first halving block or the blocks on each side of the BIP34, BIP65, CSV and segwit heights (`conformance/vectors/block-connect/README.md`).
- The `signet` suite tests the block solution check as a function of a block and a challenge. No suite delivers a signet block through `chain_process_block`, so where an implementation runs the check among a block's other checks (chapter 13: right after proof of work) is not tested.
- The low-work headers synchronization of Bitcoin Core (download, prove, download again) is described but not implemented by the reference; for honest peers the stored result is the same.
- Out of scope by design: the BIP324 encrypted transport, transaction relay and mempool policy, compact blocks, address relay, mining and wallets.
- No test suite proves the absence of divergence. These results are strong evidence, not a proof.
