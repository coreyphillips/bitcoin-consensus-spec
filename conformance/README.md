# Conformance

Tooling that checks an implementation of the specification against Bitcoin Core v32.1
(commit `f0de87f040621468b956f01f526a43a010310501`).

| Path | What it is |
|---|---|
| `PROTOCOL.md` | The JSON-lines protocol between the runner and an implementation's harness program |
| `oracle-core/` | `oracle-core-harness`: a harness whose answers come from Bitcoin Core v32.1's own C++ consensus code, compiled from source |
| `runner/` | `bcs-conformance`: starts a harness, runs the suites, derives expectations from the oracle |
| `vectors/core/` | `script_tests.json`, `tx_valid.json`, `tx_invalid.json`, `sighash.json`, `bip341_wallet_vectors.json`, byte-identical to Core v32.1's `src/test/data/` |
| `vectors/qa-assets/` | `script_assets_test.json` from the bitcoin-core/qa-assets repository |
| `vectors/bip340/` | `test-vectors.csv` from BIP340 |
| `vectors/derived/` | Core's verdict for every script query of the files above, under all 64 consensus flag combinations (generated by `bcs-conformance derive`) |

The runner does not depend on the reference crate: it must stay independent of what it tests.

## Building the oracle

`oracle-core` is a standalone crate (excluded from the workspace). Its `build.rs` compiles Core's
consensus sources and Core's bundled libsecp256k1 with the `cc` crate. It needs git and a C++20
compiler, and a Bitcoin Core checkout named by `BITCOIN_CORE_SRC`:

```sh
git clone --depth 1 --branch v32.1 https://github.com/bitcoin/bitcoin.git bitcoin-core-v32.1
cd conformance/oracle-core
BITCOIN_CORE_SRC=/path/to/bitcoin-core-v32.1 cargo build --release
# binary: conformance/oracle-core/target/release/oracle-core-harness
```

The build stops with an explanation when `BITCOIN_CORE_SRC` is unset, is not a git checkout, is not
at commit `f0de87f0...`, or has local modifications under `src/`. It compiles
`script/interpreter.cpp` (inside `cpp/oracle.cpp`, which gives it Core's `SignatureHash`,
`SignatureHashSchnorr` and static `VerifyTaprootCommitment` unchanged), `script/script.cpp`,
`primitives/transaction.cpp`, `consensus/tx_check.cpp`, `pubkey.cpp`, the hash functions and
libsecp256k1 configured as Core configures it. Only Core's portable SHA-256 code is used
(`DISABLE_OPTIMIZED_SHA256`; same results). `cpp/check.cpp` defines the assertion handlers of
`util/check.h` without Core's version banner.

What each operation calls:

| Operation | Core code |
|---|---|
| `script_verify` | `VerifyScript` with a `TransactionSignatureChecker` over a `PrecomputedTransactionData` initialised with all spent outputs, `MissingDataBehavior::FAIL` |
| `tx_check` | deserialization with witnesses allowed (trailing bytes or any decoding error: `tx-decode`), then `CheckTransaction`; `reason` is its reject reason |
| `sighash_legacy` | `SignatureHash(scriptCode, tx, index, hashType, 0, SigVersion::BASE)`, as `sighash_tests.cpp` |
| `sighash_taproot` | `SignatureHashSchnorr` with a `ScriptExecutionData` built from the request (key path without `leaf_hash`); spent outputs precomputed with `force=true` |
| `taproot_commitment_verify` | the control block size rule of `VerifyWitnessProgram`, `ComputeTapleafHash`, `VerifyTaprootCommitment` |
| `schnorr_verify` | `secp256k1_xonly_pubkey_parse` and `secp256k1_schnorrsig_verify` (any message length) |

Chain operations answer `unsupported_op`. `info` reports `spec_version` `v32.1`, plus `core_commit`
and a `build` string (compiler, target, profile) that `derive` records as provenance.

Script error identifiers are the names of the `script_errors[]` table in
`src/test/script_tests.cpp`. Errors that table lacks use the `ScriptError` enumerator name without
`SCRIPT_ERR_` (for example `UNKNOWN_ERROR`, `SCHNORR_SIG`, `TAPROOT_WRONG_CONTROL_SIZE`). The two
conventions only differ for `SCRIPT_ERR_SIG_NULLFAIL`, which is `NULLFAIL`.

The oracle also offers one operation outside the protocol, listed under `extensions` in `info`:
`x_core_script_verify` is `script_verify` accepting any of Core's flag names (policy flags
included). `derive` uses it to replay Core's own unit tests; nothing else needs it.

## Running the runner

```sh
cargo build --release -p conformance-runner
H=conformance/oracle-core/target/release/oracle-core-harness

target/release/bcs-conformance --impl "$H"                    # all suites, derived expectations
target/release/bcs-conformance --impl "$H" --raw              # original vector expectations only
target/release/bcs-conformance --impl "$H" --suite bip340,sighash --verbose
target/release/bcs-conformance suites                         # list suites
```

`--impl` is run with `sh -c`. The runner asks for `info` and runs every selected suite for which
the harness lists at least one needed operation; checks needing an unlisted operation are counted
as unsupported. Options: `--vectors DIR` (default `conformance/vectors`), `--derived DIR` (default
`<vectors>/derived`), `--timeout SECS` per response (default 120; a harness that dies or stalls is
restarted, at most 5 times), `--fail-on-level2`.

Output is one table row per suite: `cases` (checks performed), `passed`, `failed` (level 1),
`level2`, `l2-checked`, `unsupp.`. Below the table, rows without a check in the chosen mode are
listed with the stated rule and their count.

- **Level 1**: the verdict (`valid`, the sighash bytes) differs, or the harness gave no usable
  answer (`bad_request`, `internal`, malformed response, crash, timeout). Any level 1 failure makes
  the exit status 1.
- **Level 2**: the verdict matches but the error identifier (`script_error`, or `reason` of
  `tx_check`) differs from the expected one. Reported separately; affects the exit status only
  with `--fail-on-level2`. A valid answer without `script_error` counts as `OK`.

`--verbose` prints each failure (`FAIL`) and level 2 mismatch (`LEVEL2`) with the suite, the row
(0-based index into the source file's top-level array, comment rows included), the input or
witness, the flags, expected and actual values, and the row text.

## Generating derived vectors

```sh
target/release/bcs-conformance derive --oracle conformance/oracle-core/target/release/oracle-core-harness
# writes conformance/vectors/derived/{script_tests,tx_valid,tx_invalid,script_assets_test}.json
```

For every script query (each script_tests row, each input of each tx_valid/tx_invalid row, each
success and failure witness of script_assets_test.json) `derive` asks the oracle for the result
under each of the 64 consensus flag combinations, and for every tx row it records `tx_check`.
Before writing anything it checks, and stops on any disagreement:

1. **Cross-check**: every expectation the original file states for consensus-only flags (the raw
   mode checks below) must hold for the recorded answers.
2. **Core replay** (with the oracle's extension): Core's own `DoTest`, `tx_valid` and `tx_invalid`
   logic is replayed with the rows' original flags, policy flags included, with deterministic
   single-flag variations instead of Core's random ones. Every script_tests row must reproduce its
   exact expected error. This proves the runner builds each row exactly as Core's tests do, also
   for the rows whose stated expectation needs policy flags.
3. The oracle's `valid` must agree with its `script_error` (`OK` exactly when valid).

File format (`bcs-derived-script-results/1`): a header with `source`, `source_sha256`,
`provenance` (Core version and commit, the oracle's `info`), `flag_combinations` (the 64 flag
lists, in the order of Core's `AllConsensusFlags()`) and `errors`; then `tx_checks` and `scripts`,
one entry per line. A script entry has an `id` (`"12"` for script_tests row 12, `"12/0"` for input
0 of tx row 12, `"12/success"` for a script_assets witness), a `digest` (first 8 bytes of SHA-256
of the transaction, input index and spent outputs, so the runner can prove it sends exactly the
request the oracle answered) and `results`: 64 characters, one per flag combination, each indexing
`errors` through the alphabet `0-9a-zA-Z` (`OK` means valid). The runner refuses derived files whose
`source_sha256` or digests do not match.

## Flag rules

The runner only sends the seven consensus flags `P2SH`, `DERSIG`, `NULLDUMMY`,
`CHECKLOCKTIMEVERIFY`, `CHECKSEQUENCEVERIFY`, `WITNESS`, `TAPROOT`. The **64 combinations** are
those of Core's `AllConsensusFlags()`: WITNESS requires P2SH and TAPROOT requires WITNESS.

Core's vectors also use policy-only flags (`STRICTENC`, `LOW_S`, `MINIMALDATA`, `CLEANSTACK`,
`NULLFAIL`, `MINIMALIF`, `WITNESS_PUBKEYTYPE`, `CONST_SCRIPTCODE`, the `DISCOURAGE_*` flags, ...),
parsed by name as Core's `ParseScriptFlags` does (`NONE` or empty is no flag). A row with a policy
flag has a consensus-only expectation only where the rules below derive one. Derived mode does not
need any rule: every query is checked under all 64 combinations against Core's recorded verdict, so
no row is skipped.

## Suites

Raw mode checks the expectations below; derived mode checks the same queries under all 64
combinations (plus the same `tx_check`s, with Core's reject reason at level 2).

- **script-tests** (`script_tests.json`, `script_json_test`). Row
  `[[wit..., amount]?, scriptSig, scriptPubKey, flags, error, comment?]`; single-element rows are
  comments. Scripts are parsed exactly as Core's `ParseScript` (decimal numbers, `0x` raw bytes,
  `'quoted'` pushes, opcode names with or without `OP_`; checked byte for byte against Core with
  `BCS_BITCOIN_TX=/path/to/bitcoin-tx cargo test -p conformance-runner -- --ignored`). The amount
  is the exact decimal text in BTC (`ParseFixedPoint`, then `MoneyRange`). Witness elements are hex,
  `#SCRIPT# <asm>` or `#CONTROLBLOCK#`; `0x51 0x20 #TAPROOTOUTPUT#` is `OP_1 <output key>`. The
  placeholders describe a tree with one tapscript leaf (version 0xc0, the preceding witness
  element) and internal key the x-only key of secret key 1 (Core's `key0`); the control block is
  `0xc0 | parity` followed by the internal key. The query is input 0 of Core's spending
  transaction of the crediting transaction (`transaction_utils.cpp`). `CLEANSTACK` adds `P2SH` and
  `WITNESS`. Expectations: all-consensus flags give the exact result and error, success under every
  consensus subset of a passing row, failure under every consensus superset of a failing row; a row
  with policy flags that passes, passes under every subset of its consensus flags; a row with
  policy flags that fails has no raw check (rule counted).
- **tx-valid** (`tx_valid.json`). Prevouts `[txid (display order), n (int, so -1 is
  0xffffffff), scriptPubKey asm, amount (default 0)?]`; each input spends the listed outpoint. The
  flags column lists **excluded** flags. `tx_check` must pass; every input is valid (`OK`) under
  every combination containing no excluded flag.
- **tx-invalid** (`tx_invalid.json`). The flags column lists the flags that make the
  transaction fail. `BADTX` rows must fail `tx_check` and have no raw script check (rule counted;
  derived mode still checks their inputs). Other rows pass `tx_check`; if their flags are all
  consensus flags, some input fails under every superset, and every input passes once any one flag
  is removed (`TrimFlags`); rows with policy flags have no raw script check (rule counted).
- **sighash** (`sighash.json`). `sighash_legacy` with the signed 32-bit hash type must equal the
  expected hash, which the file gives in display order; `tx_check` must pass (Core checks
  `CheckTransaction` on every row).
- **bip341** (`bip341_wallet_vectors.json`). keyPathSpending: `sighash_taproot` of each listed
  input equals `intermediary.sigHash`, and that input of `auxiliary.fullySignedTx` passes
  `script_verify` with `P2SH,WITNESS,TAPROOT`. scriptPubKey: every
  `expected.scriptPathControlBlocks[i]` passes `taproot_commitment_verify` with leaf `id` `i` and
  `intermediary.tweakedPubkey`.
- **bip340** (`test-vectors.csv`). Every row, with or without a secret key: `schnorr_verify` must
  return the `verification result` column.
- **script-assets** (`script_assets_test.json`, `script_assets_tests.cpp`). The success witness is
  valid under every combination that is a subset of the case's flags, or every combination when
  `final` is true; the failure witness is invalid under every superset of the case's flags.

`corpus` (block corpus replay), `headers-live` and `interop` are reserved; they report "not
implemented yet".
