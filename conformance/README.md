# Conformance

Tooling that checks an implementation of the specification against Bitcoin Core v32.1
(commit `f0de87f040621468b956f01f526a43a010310501`).

| Path | What it is |
|---|---|
| `PROTOCOL.md` | The JSON-lines protocol between the runner and an implementation's harness program |
| `oracle-core/` | `oracle-core-harness`: a harness whose answers come from Bitcoin Core v32.1's own C++ consensus code, compiled from source |
| `runner/` | `bcs-conformance`: starts a harness, runs the suites, derives expectations from the oracle |
| `vectors/core/` | `script_tests.json`, `tx_valid.json`, `tx_invalid.json`, `sighash.json`, `bip341_wallet_vectors.json`, byte-identical to Core v32.1's `src/test/data/` |
| `vectors/qa-assets/` | `script_assets_test.json` from the bitcoin-core/qa-assets repository |
| `vectors/bip340/` | `test-vectors.csv` from BIP340 |
| `vectors/derived/` | Core's verdict for every script query of the files above, under all 64 consensus flag combinations (generated by `bcs-conformance derive`) |
| `vectors/custom/` | Targeted request and expected response pairs (`*.jsonl`) |
| `vectors/blocks/` | The block corpus: scenarios recorded from Core's functional tests (`CORPUS.md`) |

The runner does not depend on the reference crate: it must stay independent of what it tests.

## Building the oracle

`oracle-core` is a standalone crate (excluded from the workspace). Its `build.rs` compiles Core's
consensus sources and Core's bundled libsecp256k1 with the `cc` crate. It needs git and a C++20
compiler, and a Bitcoin Core checkout named by `BITCOIN_CORE_SRC`:

```sh
git clone --depth 1 --branch v32.1 https://github.com/bitcoin/bitcoin.git bitcoin-core-v32.1
cd conformance/oracle-core
BITCOIN_CORE_SRC=/path/to/bitcoin-core-v32.1 cargo build --release
# binary: conformance/oracle-core/target/release/oracle-core-harness
```

The build stops with an explanation when `BITCOIN_CORE_SRC` is unset, is not a git checkout, is not
at commit `f0de87f0...`, or has local modifications under `src/`. It compiles
`script/interpreter.cpp` (inside `cpp/oracle.cpp`, which gives it Core's `SignatureHash`,
`SignatureHashSchnorr` and static `VerifyTaprootCommitment` unchanged), `script/script.cpp`,
`primitives/transaction.cpp`, `consensus/tx_check.cpp`, `pubkey.cpp`, the hash functions and
libsecp256k1 configured as Core configures it. Only Core's portable SHA-256 code is used
(`DISABLE_OPTIMIZED_SHA256`; same results). `cpp/check.cpp` defines the assertion handlers of
`util/check.h` without Core's version banner.

What each operation calls:

| Operation | Core code |
|---|---|
| `script_verify` | `VerifyScript` with a `TransactionSignatureChecker` over a `PrecomputedTransactionData` initialised with all spent outputs, `MissingDataBehavior::FAIL` |
| `tx_check` | deserialization with witnesses allowed (trailing bytes or any decoding error: `tx-decode`), then `CheckTransaction`; `reason` is its reject reason |
| `sighash_legacy` | `SignatureHash(scriptCode, tx, index, hashType, 0, SigVersion::BASE)`, as `sighash_tests.cpp` |
| `sighash_taproot` | `SignatureHashSchnorr` with a `ScriptExecutionData` built from the request (key path without `leaf_hash`); spent outputs precomputed with `force=true` |
| `taproot_commitment_verify` | the control block size rule of `VerifyWitnessProgram`, `ComputeTapleafHash`, `VerifyTaprootCommitment` |
| `schnorr_verify` | `secp256k1_xonly_pubkey_parse` and `secp256k1_schnorrsig_verify` (any message length) |

Chain operations answer `unsupported_op`. `info` reports `spec_version` `v32.1`, plus `core_commit`
and a `build` string (compiler, target, profile) that `derive` records as provenance.

Script error identifiers are the names of the `script_errors[]` table in
`src/test/script_tests.cpp`. Errors that table lacks use the `ScriptError` enumerator name without
`SCRIPT_ERR_` (for example `UNKNOWN_ERROR`, `SCHNORR_SIG`, `TAPROOT_WRONG_CONTROL_SIZE`). The two
conventions only differ for `SCRIPT_ERR_SIG_NULLFAIL`, which is `NULLFAIL`.

The oracle also offers one operation outside the protocol, listed under `extensions` in `info`:
`x_core_script_verify` is `script_verify` accepting any of Core's flag names (policy flags
included). `derive` uses it to replay Core's own unit tests; nothing else needs it.

## Running the runner

```sh
cargo build --release -p conformance-runner
H=conformance/oracle-core/target/release/oracle-core-harness
R=target/release/reference-harness

target/release/bcs-conformance --impl "$R"                    # every default suite
target/release/bcs-conformance --impl "$H" --exclude corpus   # the oracle has no chain operations
target/release/bcs-conformance --impl "$H" --exclude corpus --raw   # original vector expectations only
target/release/bcs-conformance --impl "$R" --suite bip340,sighash --verbose
target/release/bcs-conformance corpus --impl "$R"             # same as --suite corpus
target/release/bcs-conformance suites                         # list suites
```

`--impl` is run with `sh -c`. The runner asks for `info` and runs every selected suite for which
the harness lists at least one needed operation; checks needing an unlisted operation are counted
as unsupported, and unsupported checks (or a suite with no supported operation) fail the run unless
the suite is left out with `--suite` or `--exclude` (`PROTOCOL.md` section 6). A plain run selects
every suite marked `default` by `bcs-conformance suites`: the vector suites, `custom` and `corpus`.
`headers-live`, `interop` and `peer-sync` need extra arguments and run only when named. Options: `--vectors DIR`
(default `conformance/vectors`), `--derived DIR` (default `<vectors>/derived`), `--timeout SECS` per
response (default 120; a harness that dies or stalls is restarted, at most 5 times),
`--fail-on-level2`.

Output is one table row per suite: `cases` (checks performed), `passed`, `failed` (level 1),
`level2`, `l2-checked`, `unsupp.`. Below the table come rows without a check in the chosen mode,
listed with the stated rule and their count, and per-file or per-chain details of the corpus,
headers-live and interop suites.

- **Level 1**: the verdict (`valid`, the sighash bytes) differs, or the harness gave no usable
  answer (`bad_request`, `internal`, malformed response, crash, timeout). Any level 1 failure makes
  the exit status 1.
- **Level 2**: the verdict matches but the error identifier (`script_error`, or `reason` of
  `tx_check`) differs from the expected one. Reported separately; affects the exit status only
  with `--fail-on-level2`. A valid answer without `script_error` counts as `OK`.

`--verbose` prints each failure (`FAIL`) and level 2 mismatch (`LEVEL2`) with the suite, the row
(0-based index into the source file's top-level array, comment rows included), the input or
witness, the flags, expected and actual values, and the row text.

### Known failures

An implementation that has a divergence it has accepted, or that cannot run a scenario (for
example, it lacks a network option the scenario needs), can still use the runner as a regression
gate: `--known-failures FILE` names the checks it is known to fail. Each line that is not blank and
does not start with `#` is `<suite> <location>`, where the location is what `FAIL` prints between
`[suite]` and the colon, or its start up to a space:

```text
# BIP340 messages that are not 32 bytes: no API for them.
bip340 row 15
# Equal-work tie-break after invalidateblock.
corpus feature_block.node0 check 88
# The corpus names a file's replay errors, which fail the file once, "<file> errors".
corpus mining_basic.node0 errors
interop chain feature_spec_pitfalls.node2
# A block the node accepts during initial sync although Core rejects it.
peer-sync feature_spec_pitfalls.node0 ibd 149b7d9071007e7058afe5fbfff577b06a07131dc8a24d884435fe781fd7f3fb
```

`row 15` names `row 15 (message of size 0 ...)` and not `row 150`. A failure the file names is
printed as `KNOWN` with `--verbose`, counted in `cases` but not in `failed`, and does not fail the
run; the line below the table counts them per suite. Every other failure fails the run as before.
An entry that names no failure, in a suite that ran, is printed as `STALE` and fails the run, so the
list shrinks as the implementation is fixed and never hides a check that passes. Entries of suites
that did not run are ignored, so one file can serve runs that select different suites.

## Generating derived vectors

```sh
target/release/bcs-conformance derive --oracle conformance/oracle-core/target/release/oracle-core-harness
# writes conformance/vectors/derived/{script_tests,tx_valid,tx_invalid,script_assets_test}.json
```

For every script query (each script_tests row, each input of each tx_valid/tx_invalid row, each
success and failure witness of script_assets_test.json) `derive` asks the oracle for the result
under each of the 64 consensus flag combinations, and for every tx row it records `tx_check`.
Before writing anything it checks, and stops on any disagreement:

1. **Cross-check**: every expectation the original file states for consensus-only flags (the raw
   mode checks below) must hold for the recorded answers.
2. **Core replay** (with the oracle's extension): Core's own `DoTest`, `tx_valid` and `tx_invalid`
   logic is replayed with the rows' original flags, policy flags included, with deterministic
   single-flag variations instead of Core's random ones. Every script_tests row must reproduce its
   exact expected error. This proves the runner builds each row exactly as Core's tests do, also
   for the rows whose stated expectation needs policy flags.
3. The oracle's `valid` must agree with its `script_error` (`OK` exactly when valid).

File format (`bcs-derived-script-results/1`): a header with `source`, `source_sha256`,
`provenance` (Core version and commit, the oracle's `info`), `flag_combinations` (the 64 flag
lists, in the order of Core's `AllConsensusFlags()`) and `errors`; then `tx_checks` and `scripts`,
one entry per line. A script entry has an `id` (`"12"` for script_tests row 12, `"12/0"` for input
0 of tx row 12, `"12/success"` for a script_assets witness), a `digest` (first 8 bytes of SHA-256
of the transaction, input index and spent outputs, so the runner can prove it sends exactly the
request the oracle answered) and `results`: 64 characters, one per flag combination, each indexing
`errors` through the alphabet `0-9a-zA-Z` (`OK` means valid). The runner refuses derived files whose
`source_sha256` or digests do not match.

## Flag rules

The runner only sends the seven consensus flags `P2SH`, `DERSIG`, `NULLDUMMY`,
`CHECKLOCKTIMEVERIFY`, `CHECKSEQUENCEVERIFY`, `WITNESS`, `TAPROOT`. The **64 combinations** are
those of Core's `AllConsensusFlags()`: WITNESS requires P2SH and TAPROOT requires WITNESS.

Core's vectors also use policy-only flags (`STRICTENC`, `LOW_S`, `MINIMALDATA`, `CLEANSTACK`,
`NULLFAIL`, `MINIMALIF`, `WITNESS_PUBKEYTYPE`, `CONST_SCRIPTCODE`, the `DISCOURAGE_*` flags, ...),
parsed by name as Core's `ParseScriptFlags` does (`NONE` or empty is no flag). A row with a policy
flag has a consensus-only expectation only where the rules below derive one. Derived mode does not
need any rule: every query is checked under all 64 combinations against Core's recorded verdict, so
no row is skipped.

## Suites

Raw mode checks the expectations below; derived mode checks the same queries under all 64
combinations (plus the same `tx_check`s, with Core's reject reason at level 2).

- **script-tests** (`script_tests.json`, `script_json_test`). Row
  `[[wit..., amount]?, scriptSig, scriptPubKey, flags, error, comment?]`; single-element rows are
  comments. Scripts are parsed exactly as Core's `ParseScript` (decimal numbers, `0x` raw bytes,
  `'quoted'` pushes, opcode names with or without `OP_`; checked byte for byte against Core with
  `BCS_BITCOIN_TX=/path/to/bitcoin-tx cargo test -p conformance-runner -- --ignored`). The amount
  is the exact decimal text in BTC (`ParseFixedPoint`, then `MoneyRange`). Witness elements are hex,
  `#SCRIPT# <asm>` or `#CONTROLBLOCK#`; `0x51 0x20 #TAPROOTOUTPUT#` is `OP_1 <output key>`. The
  placeholders describe a tree with one tapscript leaf (version 0xc0, the preceding witness
  element) and internal key the x-only key of secret key 1 (Core's `key0`); the control block is
  `0xc0 | parity` followed by the internal key. The query is input 0 of Core's spending
  transaction of the crediting transaction (`transaction_utils.cpp`). `CLEANSTACK` adds `P2SH` and
  `WITNESS`. Expectations: all-consensus flags give the exact result and error, success under every
  consensus subset of a passing row, failure under every consensus superset of a failing row; a row
  with policy flags that passes, passes under every subset of its consensus flags; a row with
  policy flags that fails has no raw check (rule counted).
- **tx-valid** (`tx_valid.json`). Prevouts `[txid (display order), n (int, so -1 is
  0xffffffff), scriptPubKey asm, amount (default 0)?]`; each input spends the listed outpoint. The
  flags column lists **excluded** flags. `tx_check` must pass; every input is valid (`OK`) under
  every combination containing no excluded flag.
- **tx-invalid** (`tx_invalid.json`). The flags column lists the flags that make the
  transaction fail. `BADTX` rows must fail `tx_check` and have no raw script check (rule counted;
  derived mode still checks their inputs). Other rows pass `tx_check`; if their flags are all
  consensus flags, some input fails under every superset, and every input passes once any one flag
  is removed (`TrimFlags`); rows with policy flags have no raw script check (rule counted).
- **sighash** (`sighash.json`). `sighash_legacy` with the signed 32-bit hash type must equal the
  expected hash, which the file gives in display order; `tx_check` must pass (Core checks
  `CheckTransaction` on every row).
- **bip341** (`bip341_wallet_vectors.json`). keyPathSpending: `sighash_taproot` of each listed
  input equals `intermediary.sigHash`, and that input of `auxiliary.fullySignedTx` passes
  `script_verify` with `P2SH,WITNESS,TAPROOT`. scriptPubKey: every
  `expected.scriptPathControlBlocks[i]` passes `taproot_commitment_verify` with leaf `id` `i` and
  `intermediary.tweakedPubkey`.
- **bip340** (`test-vectors.csv`). Every row, with or without a secret key: `schnorr_verify` must
  return the `verification result` column.
- **script-assets** (`script_assets_test.json`, `script_assets_tests.cpp`). The success witness is
  valid under every combination that is a subset of the case's flags, or every combination when
  `final` is true; the failure witness is invalid under every superset of the case's flags.

- **custom** (`vectors/custom/*.jsonl`). Each line is `{"name", "request", "expect"}`: the request
  (a `PROTOCOL.md` request without `id`) is sent as it is, and every field of `expect` must match
  the response, `script_error` and `reason` at level 2 and every other field (`valid`, `sighash`,
  ...) at level 1. The cases cover rules Core's vectors do not reach (see `vectors/custom/README.md`).

## Corpus suite

`corpus` replays every `vectors/blocks/*.jsonl.gz` file (or the files and directories given with
`--corpus`, repeatable) exactly as `CORPUS.md` section 4 says: `reset` becomes `chain_reset` (the
returned genesis must equal the event's), `block`, `headers` and `invalidate` become
`chain_process_block` (with `now`, `via`, and `requested` when present; blobs are read, and the
block hash, blob size and blob SHA-256 are checked), `chain_process_headers` (with `now` and
`via`) and `chain_invalidate` (with `hash` and `now`). A `restart` becomes `chain_reset` with the
restart's options followed by every block, headers and invalidate request since the last reset,
again (responses not scored); with `--restart-shortcut`, a restart whose options equal the ones in
force sends nothing. A `check` becomes `chain_tip`, plus `chain_tips` when it carries `tips` and
`utxo_hash` when it carries `utxo`.

- **Level 0** (required): tip and height at every normative check. The table's `cases`, `passed`
  and `failed` count these; a harness error or a corrupt file also fails (once per file).
- Non-normative checks are compared and reported (`L0 other`) but never fail the run.
- **Level 1** (optional): the set of (hash, height, status) chain tips. Reported only.
- **Level 2** (optional): `hash_serialized_3` and `txouts`. Counted in `level2`/`l2-checked`;
  fails the run only with `--fail-on-level2`. A harness that does not list `utxo_hash` (an
  implementation that keeps no UTXO set, `PROTOCOL.md` section 4.13) is not asked; each UTXO check
  is then counted as not compared, and the details say how many.

The details list every file with its results per level, the number of restarts and re-delivered
events, and the harness's per-event outcomes (diagnostic). With `--verbose` the first normative
divergence of each file is printed as `DIVERGE` with the check (its number, its 0-based event index
after the meta line and its file line), the expected and actual tip, and every event since the
previous check with its result, reason and the tip after it; later mismatches are printed one per
line (`FAIL`, `NONNORM`, `LEVEL1`, `LEVEL2`).

## Headers-live suite

```sh
target/release/bcs-conformance headers-live --impl "$R" --network main --peer seed.bitcoin.sprovoost.nl
```

The runner itself connects to the peer over the version 1 transport (specification chapter 14):
it sends `version` (protocol 70016, no relay), answers `version` with `verack` and `ping` with
`pong`, and downloads the whole header chain with `getheaders` (locators built like Core's
`LocatorEntries`) until a `headers` message has fewer than 2,000 entries. The harness gets
`chain_reset` for the network (its genesis must be the network's) and one `chain_process_headers`
per `headers` message, with `via: p2p` and the current time as `now`; the next `getheaders` is sent
before the harness processes the current message. The suite passes when every message is accepted
and the final `best_header` is the last header the peer sent. The details report the peer, the
height, the chain work (computed by the runner from the headers' `nBits`) and the time.

`--peer HOST[:PORT]` (default port of the network); a name is resolved and its addresses are tried
in turn. `--network` is `main` (default), `testnet3`, `testnet4`, `signet` (default challenge) or
`regtest`. A connection that fails or stalls for `--peer-timeout` seconds (default 120) is replaced,
at most 8 times, and the download resumes where it stopped. Headers that do not connect to the chain
received so far, or a discontinuous `headers` message, fail the suite.

## Interop suite

```sh
target/release/bcs-conformance interop --bitcoind /path/to/bitcoind \
  --node "target/release/reference-node --network {network} --connect {peer} --stop-at {stop_at} --options {options}"
```

For each chain the runner starts a fresh `bitcoind -regtest` in a temporary data directory with
free ports from `--port-range` (default 29000-29999; ports something listens on are skipped),
`-listen=1 -bind=127.0.0.1 -debug=net -connect=0 -v2transport=0`, no whitelist and no seeds,
loads the chain, and runs the node command (`sh -c`) with `{network}` (`regtest`), `{datadir}` (an
empty directory), `{peer}` (`127.0.0.1:<port>`) and `{stop_at}` (bitcoind's tip) substituted. It
waits for the node's `{"event":"stopped",...}` line (`--node-timeout`, default 600 seconds), checks
that the node exits with status 0, and compares `tip` and `height` with `getbestblockhash` and
`getblockcount`, and `hash_serialized_3`, when the node reports it, with `gettxoutsetinfo`. A node
that keeps no UTXO set may leave `hash_serialized_3` out (PROTOCOL.md section 5); the chain is then
counted in `level2`/`l2-checked` as not compared, which fails the run only with
`--fail-on-level2`. Without a whitelist, bitcoind disconnects a node that misbehaves; in addition,
any `Misbehaving` line in bitcoind's debug log fails the chain, even if the sync completed. The
detail line of each chain shows the transport of the node's connections (`v1`, `v2`, or both), read
from bitcoind's `New inbound peer connected: transport: ...` log lines.

`--v2transport` starts `bitcoind` with `-v2transport=1` instead, for nodes that speak only the
BIP324 version 2 transport (which this specification does not define). bitcoind then still accepts
version 1 connections, so a version 1 node passes the same way; the transport shown per chain says
which one was used. One case per chain:

- `generate-300`: `generatetodescriptor 300 "raw(51)"`;
- one chain per corpus scenario (`--corpus`, default `vectors/blocks`): the blocks of its final
  active chain (the tip of its last check, followed back to genesis) submitted in height order with
  `submitblock`, with `bitcoind` started with `-testactivationheight=name@height` and `-test=bip94`
  from the scenario's `reset` options. When a hash has several recorded byte variants (mutated
  copies), they are tried in file order until `bitcoind` accepts one; `bitcoind`'s tip must then be
  the scenario's final tip.

`{options}` in the node command (PROTOCOL.md section 5) becomes the scenario's `reset` options as
one shell-quoted JSON object (the `options` of `chain_reset`), so a node can apply the same consensus
parameters. Two stated rules exclude a scenario (counted in the report): its `reset` options are not
empty and the command has no `{options}` placeholder, because a node that does not know the
activation heights cannot accept that chain over P2P; or its final chain has blocks dated more than
two hours after the current time, which a live node with a real clock rejects. Data directories of
failing chains are kept (their path is printed); `--keep-temp` keeps all of them. The node's
standard error goes to `node-stderr.log` there, and its tail is shown on failure.

## Peer-sync suite

```sh
B=/path/to/bitcoind
target/release/bcs-conformance peer-sync --bitcoind "$B" --sync-node \
  "python3 conformance/recorder/core_sync_node.py --bitcoind $B --network {network} --datadir {datadir} --peer {peer} --options {options}"
```

The interop suite gives a node only valid blocks, and the corpus suite gives an implementation its
blocks through its harness, one call at a time. Neither reaches the code a node runs when it
validates blocks it downloaded itself, which may batch them (rbitcoin-org/rbitcoin#1537 was a
consensus split in that code). In this suite the runner is the node's only peer and serves each
scenario's blocks, including the ones Bitcoin Core rejects, through the node's own
synchronization. The node command (`--sync-node`, `PROTOCOL.md` section 5.1) is given
`{network}`, `{datadir}`, `{peer}` (the runner) and `{options}`; it has no `{stop_at}`, because the
node answers tip requests on its standard input and stops when told to.

**Cases.** For each scenario (`--corpus`, default `vectors/blocks`; the interop suite's two
exclusion rules apply), the final chain is the interop suite's. Every other recorded block whose
parent is on it is a candidate. A fresh `bitcoind -regtest` with the scenario's options gets the
final chain with `submitblock`, and while each chain block is its tip, every candidate child of it
goes to `getblocktemplate` in proposal mode: Core's checks for a block on its tip, all but proof of
work. A candidate that Core rejects in every recorded byte variant is a case, with Core's reason;
candidates Core accepts (valid side branches) and the rest are left out and counted in the
details. The corpus has 2,922 candidates; feature_taproot alone has 2,577.

**Serving.** The runner accepts the version 1 transport and BIP324 version 2 (through the
`bip324` crate; the specification does not define it), answers `version` (with `NODE_NETWORK` and
`NODE_WITNESS`), `ping` and `getheaders` (from the chain it has announced, ending with the current
case's header; a header Core rejects goes in a `headers` message of its own), and answers
`getdata` for announced blocks, `notfound` for anything else. Requested blocks go out in bursts,
all of them back to back in chain order once the node has sent no `getdata` for 50 ms. The burst
holding a case's parent also waits, up to 2 seconds, for the node to ask for the case block, which
then goes last, so the parent and the rejected block reach the node together at the end of a run
of blocks, as in initial block download.

**Checks.** Once every chain block up to the parent is delivered, and the case block too (or the
node has not asked for it within 2 seconds of having the rest), the runner sends `ping`, waits for
the `pong`, and asks for the tip. It must be the parent. When the answer is anything else, and in
the ibd mode for every answer, the runner keeps serving, asks again once the node has requested
no chain block for a second, and decides on two answers in a row that agree with no chain block
requested between them, all on one connection. A node that drops downloaded blocks after a
rejection and fetches them again, or drops the runner and connects again, is judged on where it
ends; a node asking again for a rejected block (Core does, for a block
it dropped as mutated) is still served.

Each scenario runs in two modes:

- **follow**: one node takes every case in chain order (the chain up to the parent announced with
  unsolicited `headers` messages, then the case header), then the rest of the chain, after which
  its tip must be the final tip and, after `{"op":"stop"}`, its `stopped` line must name it and it
  must exit with status 0. A failed check ends the node and the next check starts a fresh one.
  Locations: `<scenario> follow <block hash>` and `<scenario> follow final tip`.
- **ibd**: a fresh node per case, offered the chain up to the parent and the case block as its
  peer's best chain from the start, so the rejected block ends the node's initial block download.
  `--ibd-limit N` (default 32; `all` for every case) bounds the cases per scenario, evenly spaced;
  the cases left out are counted as a stated rule (the follow mode still checks them). Location:
  `<scenario> ibd <block hash>`.

A check that fails because the node did not answer (no connection, no `pong`, no tip, an `error`
line) counts like a wrong tip; after three such checks in a row the rest of the mode is reported as
`<scenario> <mode> not run`. The detail line of each scenario shows the cases, each mode's
passes, the nodes started, the transports and what was left out. `--node-timeout` (default 600
seconds) bounds each wait for the node; a node that requests nothing while blocks it needs are
missing fails after 120 seconds. A node gets the same case block at most once a second: Core asks
again, as soon as it has it, for a block that fails its context-free checks (a peer may have sent a
damaged copy), for as long as that block is on its best header chain. The data directory of a node with a failed
check is kept (the scenario's path is printed); `--keep-temp` keeps all of them.

`recorder/core_sync_node.py` runs Bitcoin Core v32.1 itself as the node (`-connect` to the runner:
a manual peer, which Core never disconnects for an invalid block), which shows that the cases and
the serving are right. The reference node cannot take this suite: its synchronization loop
(specification chapter 14 section 14.5) stops at the first invalid block, by design.
